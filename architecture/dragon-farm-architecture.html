dragon-farm: an R package for fine-tuning small language models

A CRAN-shaped R package that fine-tunes 100M to 3B parameter causal language models with LoRA, driven either from R functions or from a Shiny app where the user drags a dataset in and drags its columns into prompt and response slots.

Key decisions

Six choices shape everything else. Each one is reversible, but changing it later costs more than deciding now.

Training engine
Hugging Face transformers + peft
The de facto standard. trl was dropped during the build: its trainer API churns between minor versions, so the package uses the plain transformers Trainer with its own prompt-masking collator. Verified on transformers 5.17 and peft 0.20.
Python dependency
reticulate::py_require() in .onLoad()
Users install nothing by hand. reticulate builds an ephemeral uv environment on first use. No conda, no manual venv.
Process model
Trainer runs as a processx subprocess
Uses the uv environment's Python directly. Survives the R session, streams logs, cancels cleanly with a signal, and never blocks Shiny.
R and Python boundary
Files only: a run directory
config.json in, progress.jsonl and status.json out. Either side is testable alone, and Shiny just polls a file.
Fine-tuning method
LoRA supervised fine-tuning only, v1
Covers the "teach it my format and my domain" use case. DPO, full fine-tuning, and RL are explicit later work.
UI scope
Form plus drag-and-drop, not a node canvas
A fine-tune is a fixed pipeline. Drag-and-drop earns its place at file upload and column mapping, nowhere else.

Scope and non-goals

In scope for v1

  • Datasets from CSV, JSONL, Parquet, or an R data frame.
  • Column mapping to prompt, response, and optional system.
  • Chat-template formatting using the model's own tokenizer template.
  • LoRA training with the transformers Trainer and a collator that masks prompt tokens so only the reply contributes to the loss. Rank, alpha, dropout, and target modules exposed.
  • Background jobs with live progress, cancel, and resume-from-checkpoint.
  • Held-out loss and sample generations at the end of a run.
  • Saving adapters, merging into the base model, and generating from either.
  • A Shiny app that exposes all of the above.

Explicitly out of scope

  • Models above roughly 3B parameters. They work if hardware allows, but nothing is tuned for them.
  • Full-parameter fine-tuning.
  • DPO, ORPO, GRPO, or any preference or reinforcement method.
  • Multi-GPU or distributed training.
  • A node-graph pipeline builder.
  • Hosting the trained model as a service. Export to GGUF is a stretch goal, serving is not.

Architecture

Three layers, one file-based seam. Blue is R. Amber is Python. The dashed box is the run directory on disk that both sides read and write. Nothing crosses the seam except files and one subprocess launch.

The R API never imports transformers into the R process. reticulate is used for one thing: building the environment and reporting its interpreter path. That keeps the Shiny process light and means a crashed trainer cannot take the app down with it.

Calls py_require() with pinned lower bounds. Nothing else runs at load time.
R/python.R
One internal helper, dragon_python(), that initializes reticulate lazily and returns py_exe(). Also dragon_python_ok() for diagnostics.

Pure R. Read a file into a data frame, validate it, apply a column mapping, and write train and eval JSONL splits. No Python needed, so fully unit-testable.

S3 constructors dragon_lora() and dragon_train_args() with validation, plus the model preset table.
R/run.R · train.R · job.R
Create the run directory, serialize config, launch processx, and expose status, logs, cancel, and wait.

A real Python package with an entry point. Runnable on its own for debugging: python -m dragonfarm.train --run-dir path.

R/mod_*.R
Shiny modules live in R/ as exported-free functions so they get roxygen docs, tests, and R CMD check coverage. inst/app holds only static assets.

[{"prompt": "...", "reference": "...",
  "generated": "..."}, ...]

Exit code 0 means state is succeeded. Any non-zero exit with no error field is treated by R as a crash and the last 40 log lines are surfaced.

Run lifecycle

  1. Validate in R. dragon_train() checks the mapping, the preset or model id, and the LoRA and training args. Bad input fails here, before any Python starts.
  2. Materialize the run. Create dragonfarm_runs/<run_id>/, write the JSONL splits and config.json, and write status.json with state queued.
  3. Ensure Python. dragon_python() initializes reticulate, which resolves the uv environment on first call. First run downloads torch and friends, which is the slow step users need warning about.
  4. Launch. processx::process$new(py_exe(), c("-m", "dragonfarm.train", "--run-dir", dir)) with stdout and stderr redirected to log.txt. The process handle is stored in the dragon_run object and its pid in status.json.
  5. Train. Python loads the model, applies LoRA, and trains. The callback appends to progress.jsonl and saves checkpoints. On SIGTERM it saves once more and writes cancelled.
  6. Finish. Python writes the adapter, runs evaluation, writes samples.json, and sets state to succeeded. R's dragon_status() reads it. Since status is on disk, a fresh R session can pick up any run by path.

Mechanics worth deciding up front

  • Polling, not push. reactiveFileReader(1000, session, progress_path, read_progress) drives the chart. Cheap, robust, and it works when the app is served remotely.
  • No training in the session. The Train panel calls dragon_train(wait = FALSE). Closing the browser does not stop a run.
  • Try-it latency. A subprocess per generation is a few seconds of model load each time. Acceptable for v1. A persistent generation worker via mirai is the planned v2 fix.
  • The "Copy R code" button is the bridge from the UI to the API. Every run in the UI is reproducible as a script, which is what makes this a package and not just an app.
  • Chart library. plotly for the loss curve. It handles live updates without redrawing and is already familiar to R users.

Testing and CI

Three tiers

  • Unit, no Python. Dataset reading, mapping and glue templates, config validation, JSON serialization, run-directory creation, status parsing against fixture files. These run everywhere including CRAN.
  • Integration, gated. Skipped unless DRAGONFARM_INTEGRATION=true. Trains SmolLM2-135M on 40 rows for 6 steps on CPU, then generates one reply. Around three minutes on a GitHub runner after the environment is cached.
  • App. shinytest2 against the modules with a fake job backend that replays a recorded progress.jsonl. Verifies the bucket-list mapping produces the right chat rows and the monitor renders a finished run.

Workflows

  • R-CMD-check.yaml. The standard r-lib matrix: Ubuntu release and devel, macOS, Windows. Unit tests only.
  • integration.yaml. Ubuntu only, on push to main and nightly. Caches the uv environment and the Hugging Face hub directory so the 2 GB torch download happens once.
  • Python side. A small pytest suite under inst/python/tests for the chat-template and callback code, run in the same integration job.

Risks

RiskLikelihoodMitigation
First-run environment build downloads around 2 GB and takes several minutes. Users assume the package is broken.Highdragon_check() in the README as step one, a cli spinner with a plain message, and the app shows a setup screen before anything else.
Windows CUDA wheels for torch and the uv resolver disagree, so the GPU is not used.Confirmed during the buildPyPI ships a CPU-only torch on Windows, and uv picks the highest version across indexes, so an older CUDA index loses to PyPI. The package reads the NVIDIA driver version at load and sets UV_EXTRA_INDEX_URL to the newest CUDA index the driver supports (cu130 for driver 580 and newer). dragon_check() warns when a GPU is present but torch has no CUDA.
transformers renames TrainingArguments fields between major versions (v5 dropped warmup_ratio and torch_dtype).Mediumtrl was dropped entirely. The trainer introspects TrainingArguments at runtime and adapts; the nightly integration job catches further drift within a day.
Gated models fail with an opaque 401.MediumPresets carry a gated flag. R checks for HF_TOKEN before launch and gives a one-line fix.
bitsandbytes does not install on macOS or Windows.CertainNever in the default requirement set. Only offered when the platform supports it.
Out-of-memory mid-run on consumer GPUs.MediumPresets carry a minimum VRAM. The Model panel compares it with detected VRAM and warns. Batch size and sequence length are the first two knobs shown.
The sortable bucket list does not express "combine two columns with a separator".LowBuckets accept multiple chips and join with a newline. A text field under each bucket shows the resulting glue template for hand edits.
